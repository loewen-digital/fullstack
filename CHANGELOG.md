All notable changes to fullstack, newest first. SemVer, 0.x is pre-release. The heading
format is a contract, keep it: `## v<Version> · <YYYY-MM-DD> · <Title>`. Lines under

## v0.3.0 · 2026-09-23 · Hashed tokens, signed storage, Workers bindings

- The docs site deploys again: the deploy workflow used `cloudflare/pages-action`, which Cloudflare has removed from GitHub, so every docs change since 2026-09-14 failed to publish. It now deploys through `cloudflare/wrangler-action`.
- **Breaking:** `auth.resetPassword(token, password)` returns the user (`AuthUser | null`, like `verifyEmail`) instead of a boolean and revokes every session of that user, so a reset after a takeover logs the attacker out and the app can open a fresh session for the browser that reset the password. `auth.destroyUserSessions(userId)` does the same revocation on its own, for a "log out everywhere" action. `AuthDbAdapter` gains `deleteUserSessions(userId)`, implemented by the flatdb adapter. The auth page and the flatdb guide show both. Decision: [0015](docs/decisions/0015-password-reset-revokes-sessions.md). (#25)
- **Breaking for adapters:** issuing a one-time token deletes the user's earlier tokens of that type, so only the most recently sent verification or reset link works; a verification mail to a previous address no longer verifies the current one. A token that is presented is deleted, consumed or expired, so `tokens` holds at most one live token per user and type and nothing piles up for active users. `AuthDbAdapter` gains `deleteToken(id)` and `deleteTokens(userId, type)` and loses `markTokenUsed(id)`; `AuthToken.usedAt` is gone (the flatdb adapter stops writing it, a leftover field in existing documents is ignored). Decision: [0014](docs/decisions/0014-one-time-tokens-deleted-not-marked.md). (#26)
- **Breaking:** `RateLimiter.check` and `reset` return promises on every limiter, the memory one too, so app code awaits them: `const { allowed } = await limiter.check(key)`. `remaining` and `resetAt` on the result are optional: the memory counter reports them, a store that cannot does not, and the type says so. (#29)
- `createBindingRateLimiter({ binding })`, or `createSecurity({ rateLimit: { binding } })` with `security.createRateLimiter()`, runs the rate limiter on Cloudflare's Rate Limiting binding inside a Worker, so a limit holds across isolates instead of counting anew in each one. `check(key)` reports `allowed` from the binding and invents no count or reset time; `reset(key)` does nothing, the binding has no reset. The limit and its period of 10 or 60 s are the binding's `ratelimits` entry in the wrangler config; `windowMs` and `max` next to `binding` are a type error. The binding is typed structurally as `RateLimitBinding` and checked against `@cloudflare/workers-types`; the security page shows both limiters and what the binding does not report. Decision: [0013](docs/decisions/0013-rate-limiter-one-interface-two-factories.md). (#29)
- The S3 and R2 storage drivers sign every request with AWS Signature V4 through `crypto.subtle` (no SDK, no `node:*`), so a private bucket works. Before, `createS3Driver` sent `x-amz-date` and no `Authorization`, and `createR2Driver` took keys it never used, so GET, PUT, HEAD, DELETE and LIST answered 403 on anything but a public bucket. `createR2Driver` is the S3 driver on `https://<accountId>.r2.cloudflarestorage.com` with region `auto`; `createS3Driver` takes `endpoint` and `forcePathStyle` for MinIO and other S3-compatible services. Keys go on the URL encoded once per segment (`a b.png` is `a%20b.png`), also in `getUrl` and under `publicUrl`; the keys of a listing are XML-unescaped; `exists` throws on a status other than 200 or 404 instead of answering `false` to a 403; `put` reads a stream into memory before the upload. The signer is checked against the worked examples in the S3 API reference, the drivers against a `fetch` that re-signs what it receives. Decision: [0012](docs/decisions/0012-storage-uploads-buffered.md). (#28)
- `createR2BindingDriver({ bucket, publicUrl? })` runs storage on the R2 bucket binding inside a Worker, without keys or signing: `get`, `put` with bytes, a string or a stream and `contentType`, `delete`, `exists`, `list(prefix)` across every page, and `getUrl` as `publicUrl/key` (a binding has no URL, so it throws without `publicUrl`). The binding is typed structurally as `R2BindingBucket`; a test checks that slice against `@cloudflare/workers-types`, a devDependency only, and the docs samples type-check against the same `R2Bucket`. The storage page shows the driver and drops the "write your own" note. (#28)
- **Breaking for stored data:** session tokens and one-time tokens are stored as their SHA-256 hash; the raw token only travels in the cookie or the mail. `AuthDbAdapter` receives the hash in `createSession`/`createToken` and is queried with it in `findSession`/`deleteSession`/`findToken`, so a bucket listing, a backup or a log line of the auth collections logs nobody in and resets no password; the adapter interface itself is unchanged. `createSession` and `validateSession` return the session with the raw token, so `setAuthCookie(session.token)` and `destroySession(authSession.token)` work as before. Sessions and pending verification or reset tokens written before this version stop validating: users log in again, mails from before the upgrade are requested anew. `hashToken(raw)` is exported from `@loewen-digital/fullstack/auth` for code that has to find the record behind a token. Tokens come from Web Crypto (`crypto.getRandomValues`, `crypto.subtle`), so `node:crypto` in `auth` is scrypt only. Decision: [0011](docs/decisions/0011-tokens-stored-hashed.md). (#27)

## v0.2.0 · 2026-09-14 · Adapters expose the session only, config keys all read

- The docs site is the `docs/` project itself (`docs/package.json`, `docs/.vitepress/`, pages in `docs/content`) instead of `docs/vitepress` with `srcDir` pointing out of the project: `cd docs && npm ci && npm run build` now works next to the repository's own `node_modules`, where it failed on `estree-walker`, and the resolve workaround in the config is gone. The deploy workflow runs `npm ci` in `docs`. (#24)
- `FullstackConfig` promises only what the factories read: `db.seeds`, `mail.templates`, `storage.basePath` and `logging.transport` are gone (nothing read them; `seed` takes its file as an argument), `security` and `i18n` are the modules' own config types instead of diverging copies, so `createStack({ i18n: { locale: 'de' } })` builds a German instance where `{ defaultLocale: 'de' }` used to compile and yield English, and `rateLimit.windowMs` is a number. `csrf.ttl` and `i18n.directory`, declared and never read, are gone from the module types too. (#20)
- `storage.get` returns `Uint8Array<ArrayBuffer>`, so the bytes go straight into `new Response(bytes)` and `new Blob([bytes])` under TypeScript 5.9 with `strict: true`; before, the wider `Uint8Array` (`ArrayBufferLike`) was rejected there. The memory driver and the fake storage driver copy what `put` receives onto a buffer of their own, so no driver hands out a view on the caller's buffer or a `SharedArrayBuffer`. (#17)
- Nuxt adapter: the session cookie and `setAuthCookie` carry `Secure` when the request came over HTTPS, read from `x-forwarded-proto` (a proxy in front of Nitro) or the TLS socket; before, the session cookie never had it and `setAuthCookie` defaulted to `false`. `secure` on `createNuxtMiddleware`'s options or on `setAuthCookie` overrides the detection, `isSecureRequest(event)` exposes it. (#19)
- The adapters no longer put a `user` on `locals` (SvelteKit, Astro), `event.context` (Nuxt) or the loader args (Remix). It was `{ id, email: '' }`, invented from the session because the adapter has no user store, and its `AuthUser` type carried `passwordHash`, one `return { user }` away from the client. `authSession.userId` is the key; load the user yourself, as the quick start and the guide do. Decision: [0010](docs/decisions/0010-no-user-on-locals.md). (#9)
- `bin.fullstack` is `dist/cli/index.js` without the leading `./`: npm normalized it at every publish and warned that the entry was "invalid and removed", which it was not; the published 0.1.0 has the binary.
## v0.1.0 · 2026-09-14 · First release

- Releases: `release.yml` skips `npm publish` when the tagged version is on npm already and still creates the GitHub Release, so the first version, published by hand before the trusted publisher exists, gets its release from the tag push like every later one. `npm publish` runs `npm run build` first (`prepublishOnly`), so a stale or missing `dist/` cannot ship.
- The docs site builds again: the mail page's `{{ name }}` placeholders in prose read as Vue interpolations to VitePress, so the site had not updated since the Nuxt/Remix/Astro pages (#11); every page since is live once this deploys.
- Memory cache driver: in dev mode (`NODE_ENV` not `production`) every `createCache({ driver: 'memory' })` added a `process` exit listener and a permanent entry in the Dev UI's cache registry, so an app that builds a cache per request leaked both, and Node warned about the listeners from the eleventh cache on. The registry now holds caches weakly and drops the ones the app let go; there is no exit listener.
- Tooling: `npm audit` is clean apart from one low finding. `npm audit fix` patched the transitive packages, `vitest` is on 4 (every 3.x carries the `@vitest/mocker` file-read advisory), and `vite-plugin-dts` is gone from the build: `tsc -p tsconfig.build.json` already writes the same declarations (byte-identical, checked), and the plugin pulled in `@microsoft/api-extractor` with its `lodash`. What stays: `cookie` below 0.7 behind `@sveltejs/kit` (GHSA-pxg6-pf52-xh8x), which the latest kit still pins; kit is a devDependency used only by the SvelteKit type-mirror test, its code never runs here. (#23)
- `db` is the module for apps on a SQL database, Node-only, and nothing defaults to it any more: `createTestStack()` no longer opens a SQLite database, `createTestStack({ db: { driver: 'sqlite', url: ':memory:' } })` adds one (typed `TestStackWithDb`). `drizzle-orm` is an optional peer dependency like `better-sqlite3`, so the package has no dependencies of its own and an app on flatdb installs neither. The db, testing, installation and README pages say so; the package's own apps keep their data in flatdb and call it directly. Decision: [0009](docs/decisions/0009-flatdb-is-the-store-db-is-opt-in.md). (#22)
- The README, which npm shows as the package page, describes what ships: install and what to add per driver, a stack, the SvelteKit hook and `validate` as they are today, one table per module and per adapter with the factory and drivers each exports, testing, CLI, Vite plugin and Dev UI, the runtime requirements. The sync `validate`, `db.query`, `createDb({ schema })`, `createStack(config)` without `authDb` and the other calls it showed do not exist. Its ```ts blocks are type-checked by the docs test like the docs pages.
- `createDb` and the `sqlite-fts` search driver work from the built package: both loaded `better-sqlite3` with a bare `require`, which the ESM build shipped as is, so every consumer (and `fullstack migrate`/`seed`) got `require is not defined`; the test suite runs the source through vitest and did not see it. `npm run build` now ends with a smoke run that imports every subpath of `dist/` under Node ESM and opens both sqlite entry points.
- `better-sqlite3` is an optional peer dependency instead of a dependency: `npm install @loewen-digital/fullstack` compiles no native module any more. Apps that use the `sqlite` db driver or `sqlite-fts` search install it themselves; the factories throw with that hint when it is missing, and `createTestStack` opens its database on first access so tests without `db` need nothing. Decision: [0008](docs/decisions/0008-better-sqlite3-optional-peer.md). The db module's future next to flatdb is #22.
- The Vite plugin, Dev UI and CLI pages describe what ships: `fullstackPlugin({ configRoot, generateTypes })`, the `virtual:fullstack/config` module and the generated `fullstack.d.ts`, the Dev UI at `/__fullstack/` in `vite dev` only with its five panels and where their data comes from, and the CLI's `migrate`, `migrate:rollback`, `migrate:status`, `seed [file]` and `generate migration|factory|seed`. The `fullstack()` export, the `devUI` option, `migrate:generate`, `db:seed`, `db:fresh`, `generate:factory` and `generate:seeder` the pages showed do not exist. Their samples are type-checked by the docs test; every page under `docs/content/` with a ```ts block is now covered. (#15)
- `fullstack generate factory <name>` scaffolds the shape `defineFactory` takes (one function per field with a `sequence`); before, the file used a `definition` key and did not compile. `AnyDrizzleDb` is exported from `@loewen-digital/fullstack/db`, so the migration scaffold's import resolves.
- The testing pages describe the API the package exports: `createTestStack` and what it holds, `fakeMail`/`fakeQueue`/`fakeStorage` with `sent`, `lastSent`, `sentTo`, `sentWithSubject`, `dispatched`, `failedJobs`, `keys`, `size` and `clear` asserted with the test runner's `expect`; `withSavepoint`, `createDbCleaner` and `seedOnce`; `defineFactory` with `make`/`makeMany`/`state`, `sequence` and `pick`, and inserting the records with Drizzle. The `assertSent`-style helpers, `createSeeder` and `db.query` the pages showed do not exist. Their samples are type-checked by the docs test. (#14)
- The notifications, permissions, queue, realtime, search and webhooks pages describe the API the package exports: `notify(user, notification)` with `channels()` and the `toMail`/`toInApp`/`toSms`/`toPush` methods and the in-memory in-app store; roles with wildcards and inheritance, `definePolicy` and how `can` chooses between policy and roles; `dispatch({ name, payload })`, `handle`, `process()` and the retry/dead-letter behaviour, with what the drivers do not enforce; channels and `sse()` on a `ReadableStream` response; `index`/`search`/`delete`/`flush` with the SQLite phrase matching and the Meilisearch/Typesense driver factories; `verify` and `send` with retries and the delivery log. Their samples are type-checked by the docs test. (#13)
- The validation, db, cache, logging, mail, storage, events and i18n pages describe the API the package exports: async `validate` with pipe-string and object rules, the built-in rule list, inferred `data` types and `defineRules`; `createDb(config, schema)` with `drizzle`, `migrate`/`rollback`/`migrationStatus`, `seed`, `factory` and `paginate` as metadata; `remember(key, ttl, fn)` and the Redis/KV driver factories; `createLogger` with its three transports and `child`; `createMailInstance` with the SMTP/Resend/Postmark factories, `render` and `sent`; `createStorageInstance` with the local/S3/R2 factories and `getUrl` per driver; the event bus's `on`/`once`/`off`/`emit` semantics; `t`/`tn`/`locale`/`number`/`date` and `loadTranslations`. Their samples are type-checked by the docs test. (#12)
- The Nuxt, Remix and Astro adapter pages describe the API the package exports: `createNuxtMiddleware` on `event.context`, `createRemixLoader`/`createRemixAction` with `commitSession()` and the cookie header helpers, `createAstroMiddleware` on `App.Locals`; login, logout and CSRF with each adapter's `setAuthCookie`/`authCookieHeader`, `getCsrfToken` and `validateBody`; the options and helpers tables. Their samples are type-checked by the docs test against stubs of h3, Remix and Astro. Decision: [0007](docs/decisions/0007-framework-stubs-in-docs-harness.md). (#11)
- Nuxt adapter: a response with two cookies (the session cookie from the middleware plus `setAuthCookie` from a login handler) carried both in one comma-joined `Set-Cookie` header, which browsers read as one malformed cookie; the auth cookie was lost. Each cookie is now its own header.
- Nuxt and Astro adapter types accept the frameworks' own objects: `H3Event.node.res.getHeader` may return a number, `setHeader` takes an array, `AstroAPIContext.locals` is `object` (Astro's `App.Locals` has no index signature) and `AstroCookies.headers()` is any iterable.
- The getting-started pages (installation, quick start, configuration) and the core-concepts pages (factory functions, driver pattern, web standards) describe the API the package exports: the quick start builds register, login, a guarded page and logout on flatdb with `createHandle` and `validateForm`; configuration explains named drivers versus `createXDriver` into `createXInstance`, `env()` with typed fallbacks and `createStack(config, { authDb })`; the driver table lists what each module actually ships and which Node APIs remain (scrypt, sqlite, fs, SMTP). Their samples are type-checked by the docs test. `DbConfig` is exported from `@loewen-digital/fullstack/db`. (#10)
- The security page describes the API the package exports: `createSecurity` with `generateCsrfToken`/`verifyCsrfToken`, `corsHeaders`, `createRateLimiter` and `sanitize`, the standalone functions, and the options the factory reads. Its samples are type-checked by the docs test; the harness moved to `src/__tests__/docs-harness.ts` so a sweep over other pages can reuse it.
- The auth-on-flatdb guide's samples are type-checked by the docs test as well; the Workers globals `R2Bucket` and `ScheduledEvent` are stubbed on flatdb's `R2BucketLike`.
- `createSecurity()` refuses to generate or verify CSRF tokens without `csrf.secret`; before, a built-in default signed them, so anyone reading the source could mint a token for any session. CORS, rate limiting and `sanitize` keep working without a secret. Decision: [0006](docs/decisions/0006-csrf-secret-required.md).
- The auth, session and SvelteKit adapter pages describe the API the package exports: `createAuth(config, { db })` with `hashPassword`/`verifyPassword`, `createSession`/`validateSession`/`destroySession`, the email verification, password reset and one-time token flows and `oauthProvider`; the session manager's `open`/`commit` request cycle, the handle, the three drivers and the `driver`/`secret`/`maxAge` options; `createHandle` with `App.Locals` typing, guarding a page, login and logout with `setAuthCookie`/`clearAuthCookie`/`validateForm`, CSRF, the handle options and helpers. Every ```ts block on the three pages is type-checked by a test against `src/` as a SvelteKit 2 project would compile it (`src/__tests__/docs.test.ts`; a `// <path>.ts` first line makes a block a file, other blocks share one module per page). `RedisClient` is exported from `@loewen-digital/fullstack/session`. Decision: [0005](docs/decisions/0005-docs-samples-typechecked.md). (#7)
- The cookie session driver is stateless: through `createHandle`, flash and old input travel in the signed `fsid` cookie and survive a new process or a new Workers isolate. A tampered, unsigned or foreign cookie opens an empty session, as does one older than `maxAge` (default two hours). `createSession({ driver: 'cookie' })` now requires `secret`; before, a built-in default signed the cookie. The session page and the auth-on-flatdb guide drop the round-trip workaround. Decision: [0004](docs/decisions/0004-stateless-cookie-session.md). (#6)
- Session API for request cycles: `SessionManager.open(cookie)` returns the handle for a session cookie's value and `commit(handle)` saves it and returns the value the response cookie has to carry, the id with memory and redis, the signed payload with cookie. All four adapters (SvelteKit, Nuxt, Remix, Astro) use the pair. `SessionDriver` gained optional `serialize(id, data)`/`parse(value)` for stateless drivers; the cookie driver's `serialize`/`parse` changed accordingly, its `read`/`write`/`destroy` do nothing, and non-ASCII values round-trip. `handle.destroy()` also clears the session's data, so a later `save()` or `commit()` writes an empty session. (#6)
- SvelteKit adapter: `createHandle`, `setAuthCookie` and `clearAuthCookie` take SvelteKit's own `RequestEvent` and `Handle` under `strict: true`. `export const handle: Handle = createHandle(stack)` and `sequence(createHandle(stack), other)` compile, and `App.Locals` can be any interface, index signature or not. The adapter types only the slice of SvelteKit it uses (`locals` is `object`, `cookies` has `get`/`set`/`delete`, `resolve` is a method signature); a test checks that slice against `@sveltejs/kit`, which is a devDependency only. The auth-on-flatdb guide hands the request to `createHandle` and sets the auth cookie with the adapter's helpers again. (#8)
- Guide [Auth on flatdb](docs/content/guides/auth-on-flatdb.md): `auth` on `@loewen-digital/flatdb` collections with zod schemas, the `session` module on the cookie driver and its limits, Cloudflare Workers (R2 binding, `nodejs_compat`, one database per request), local development (`FsAdapter`, `MemoryAdapter` in tests) and the expired-session sweep. The session page now says the cookie is signed, not encrypted. `createHandle` does not yet carry the cookie driver's payload in the cookie (#6) and the adapter's types reject SvelteKit's `RequestEvent` (#8), so the guide round-trips the session cookie and validates the auth cookie in app code; both spots are marked `UPSTREAM`. Decision: [0003](docs/decisions/0003-cookie-session-round-trip-in-guide.md). (#4)
- `@loewen-digital/fullstack/auth/flatdb`: `createFlatdbAuthAdapter({ users, sessions, tokens })` runs `createAuth` on the app's own `@loewen-digital/flatdb` collections (auto mode). flatdb's `_id` is the user id, dates are stored as ISO strings and come back as `Date`. flatdb is an optional peer dependency; the adapter imports nothing from it, so `@loewen-digital/fullstack/auth` stays as it was. (#3)
- Login removes the user's expired auth sessions: `createSession` calls `AuthDbAdapter.deleteExpiredSessions(userId)` before it inserts the new one, so the session store stays bounded without a scheduled job. Decision: [0002](docs/decisions/0002-expired-sessions-on-login.md). (#3)
- The `AuthDbAdapter` docs and the `createStack` error no longer say the adapter is written against a Drizzle schema; it is storage-agnostic.
- Releases run from tags: pushing `v<version>` runs lint, typecheck, tests and build, publishes to npm through trusted publishing (no token, provenance included) and creates the GitHub Release with this file's matching section as notes. The tag must equal the version in `package.json`. Replaces `publish.yml` (token-based) and `changelog.yml` with `cliff.toml` (notes generated from commit messages). Decision: [0001](docs/decisions/0001-release-on-tag.md).
- `repository`, `bugs`, `homepage` in `package.json`, so npm shows the source and can attest provenance.
- Node 24 is the required version (`engines.node` in `package.json`); CI, deploy and the agent workflow read it from there.
- Design for running `auth` on `@loewen-digital/flatdb` (Cloudflare R2 in production) is decided: a reference `AuthDbAdapter` on the app's own collections, shipped as its own subpath without importing flatdb. The `session` module stays on the cookie driver; a flatdb session driver (one object per session through flatdb's `StorageAdapter`) is designed but parked until an app needs server-side session state. Decision: [ADR 0001](docs/adr/0001-flatdb-driver.md). (#1, #2)
- Agent rules live in `AGENTS.md`; `CLAUDE.md` only imports it. The Codex review rules are a section of the same file.
